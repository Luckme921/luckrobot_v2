# LuckRobot 顶部碰撞包络深度避障 V12.10

V12.10.9 分析 300 秒动态包后确认，5点最近表面支持已显著改善深度投影，但仍有
4～5束、约0.408 m的持续窄假点。即时安全滤波原本恰好允许4束，因此偶尔触发
Collision Monitor；规划确认虽然要求7束，却只按角度索引连续性分簇，窄近点紧邻
远墙回波时会被错误拼接并由6/16秒记忆放大。现在即时安全门槛为6束、相邻量程
容差0.08 m；规划层确认提高为5帧，并在相邻束量程相差超过0.08 m时强制分簇。
真实障碍在同一包内通常形成几十到数百束连续回波，因此该调整保留了充分余量。

V12.10.8 根据真实导航绕障测试，将已确认相机障碍的局部/全局世界坐标记忆从
3/8 秒加倍到 6/16 秒。原参数有时会在车体尚未完全越过高位障碍时到期，使
LuckGrid 再次选择穿越障碍的最短路径。新值优先保证静态家具和悬空结构的安全
绕行；人员或移动物体离开后，局部层最多保守约 6 秒、全局层最多约 16 秒。

V12.10.7.1 将已通过静态 A/B 的配置冻结为默认值：最近表面支持数 5，深度障碍
高度范围 0.12～0.50 m。空场 `/scan_camera` 的最近点 p05 已由旧假点 0.472 m
恢复到约 0.843 m；真实平板仍以 8～12 个支持点进入即时流和规划流。最低高度
0.12 m 略高于主 2D 雷达约 0.11 m 的扫描平面，两种传感器形成小幅重叠。

V12.10.7 根据实车静态 A/B 数据将最近表面支持阈值从 3 调整为 5：空旷时
0.47 m 假点的支持数中位数为 4，而约 0.41 m 真实平板为 48。该调整只改变
单个角度束内的同表面深度支持要求；即时安全流仍要求 4 个相邻角度束，规划流
仍要求 7 束且连续确认 4 帧。RViz 默认新增两路不同颜色的相机扫描显示。

V12.10.6 修复持续近距飞点能够绕过点数阈值的问题。旧算法先取每个角度束的最近
距离，却用该束内所有距离的点计算数量；一个 0.47 m 飞点与同束内多个远处墙面点
会被错误合并，最终仍由最近飞点进入安全链。现在先求最近距离，再只统计与最近
表面相差不超过 0.03 m 的支持点，至少 3 个同深度采样才生成该束。支持数写入
LaserScan intensity 便于后续诊断。该空间/深度一致性判断负责持续噪声；4帧世界
坐标确认只负责短时噪声，不能靠无限增加帧数消除永久假点。

V12.10.5.2 修复 `/scan_camera` 有约 15 Hz 消息但没有可见点的问题。实车日志显示
高度投影每帧有约 430～450 个有效束，但 Gemini 图像时间戳经常领先最新
`odom -> base_footprint` TF 约 0.05～0.9 秒，478 帧中有 434 帧精确时刻查询失败，
确认节点因此发布了全 `inf` 的空扫描。现在先尝试图像时刻 TF；若发生 future
extrapolation，则立即使用最新可用 TF 完成低速运动补偿，并分别统计 fallback 与
真正无 TF 的帧数。同时 `/scan_camera` 从 Best Effort 改为 Reliable，解决 RViz
LaserScan 显示的 QoS 不兼容；Nav2 的 Best Effort 订阅仍可接收 Reliable 发布者。

V12.10.5.1 修复确认节点启动即退出的问题。Humble `rclpy` 的日志函数不接受
额外的 printf 位置参数，V12.10.5 的三处日志调用因此在节点构造阶段触发
`TypeError`，导致 `/scan_camera_safety` 保持约 15 Hz，但 `/scan_camera` 发布者为
0。日志现已改为预格式化字符串，规划确认同时调整为 4 帧/0.50 秒。诊断脚本也会
在任一路扫描没有发布者时直接拒绝录包，不再产生看似成功但缺少规划扫描的记录。

V12.10.1 补充：Orbbec 若未向新建的 Python TF 监听器提供
`camera_depth_optical_frame`，节点会自动使用已有的 `camera_depth_frame`，并按照
REP-103 完成光学坐标到相机机身坐标的轴变换。日志会打印实际采用的 TF 帧。

V12.10.2 修复：不再覆盖 `rclpy.Node` 内部 `_subscriptions` 列表。V12.10.1
因此错误地移除了 TF Listener 的订阅，表现为图像持续接收但 `base_footprint`
永远不存在；该问题与 URDF 外参无关。

V12.10.3 补充动态全局重规划：高度扫描继续以 2.5 m 范围进入局部代价地图和
Collision Monitor，同时以 1.5 m 障碍范围、2.0 m 清除范围进入全局代价地图。
因此机器人背对高位障碍时，初始全局路径仍可能暂时穿过未知障碍；机器人转向、
相机第一次真正看见障碍后，局部控制器会立即避让/停车，随后 0.5 Hz 的行为树重
规划会让 LuckGrid 根据更新后的全局代价地图替换主路径。这是视场受限传感器的
正常因果顺序，不使用未观测数据猜测障碍位置。

相机点云仍保持关闭。当前节点直接从 640×400 深度图按行步长 2 做向量化三维
恢复，仅发布 641 束 LaserScan；这比让 Orbbec 额外生成并通过 DDS 搬运完整
PointCloud2 更适合 8 GB Jetson。语义建图将来需要点云时应使用独立档位开启，
不应让彩色点云成为基础避障链的常驻依赖。

V12.10.4 增加视场滞回：实车验证发现机器人开始绕过高位障碍后，障碍会离开前向
深度相机的水平视场，新清除射线随即删除该障碍，下一轮全局规划又选择原直线，
形成来回改路。现在局部相机观测保留 3 秒，全局相机观测保留 8 秒。保留的是已
变换到 odom/map 坐标系的障碍观测，不是把障碍固定在机器人前方；机器人转向后
障碍仍停留在正确的世界位置。动态物体移走后记忆会自动过期，不会永久污染地图。

V12.10.5 修复“短时深度噪点被障碍记忆放大”。高度投影首先要求同一角度格至少
有 2 个深度像素支持，然后形成两路扫描：`/scan_camera_safety` 要求至少 4 束连续、
相邻量程差不超过 0.12 m，再直接进入 Collision Monitor；`/scan_camera` 在
`odom` 坐标中补偿机器人运动，
只有连续 4 帧、0.50 秒窗口内位置一致且横向连续不少于 7 束的回波才进入局部和
全局代价地图。局部 3 秒/全局 8 秒的记忆继续保留，但只记忆已经确认的障碍物。
单帧飞点不会再被规划器当成长寿命障碍；真实细小物体即使暂时未进入规划层，仍会
由即时安全流触发减速或停车。

```text
/scan_camera_raw
  -> 轻量空间滤波 -> /scan_camera_safety -> Collision Monitor（即时安全）
                     -> 世界坐标连续 4 帧确认 -> /scan_camera -> Nav2 代价地图（规划）
```

## 结论

原 `/scan_camera` 由 640×400 深度图中央 60 行生成，只覆盖图像高度的 15%。
相机光心约离地 0.356 m，而机器人最高结构约离地 0.47 m。中央窄带只能代表
相机附近的一层水平切片，不能保证发现位于相机上方的桌沿、横梁或悬空障碍。

V12.10 新增 `depth_height_scan`：把深度像素恢复成三维点，利用 TF 变换到
`base_footprint`，只保留离地 0.04～0.50 m 的点，再投影为平面 LaserScan。
这样覆盖的是机器人的真实高度包络，地面则由最小高度阈值排除。

## 三种模式

- `legacy`：原中央 60 行扫描，保持现有稳定基线；默认值。
- `shadow`：原 `/scan_camera` 继续负责安全；新算法仅发布
  `/scan_camera_height`，不控制小车。
- `height`：新算法发布到既有 `/scan_camera` 安全链，正式接管。

## 首次验证（禁止启动自动探索）

启动旁路模式：

```bash
ros2 launch my_robot_bringup luckrobot_system.launch.py \
  mode:=mapping navigation_profile:=luck_full \
  depth_obstacle_mode:=shadow
```

确认两个扫描均有数据：

```bash
python3 ~/ros2_ws/tools/check_depth_height_scan.py --duration 10
```

让机器人保持静止，在机器人正前方约 0.30～0.45 m 依次放置一块平板：

1. 平板覆盖离地 0.05～0.15 m；
2. 平板覆盖离地 0.25～0.35 m；
3. 平板覆盖离地 0.40～0.50 m（模拟桌沿/顶部碰撞物）。

每个高度分别运行一次检查脚本并保存完整输出。第三组中
`/scan_camera_height` 应稳定给出接近实测距离的前向值；它的量距原点是机器人中心
`base_footprint`，而旧 `/scan_camera` 的量距原点在前置相机，因此新值通常会比旧值
大约 0.14～0.16 m，这不是误差。旧扫描很可能看不到第三组，这是预期的 A/B
差异。无障碍时还需确认新扫描没有持续出现 0.20 m 内的假障碍；否则不能切换正式
模式，应先调高 `depth_min_obstacle_height`。

## 正式低速验收

三组静态测试通过后，才用下列命令切换：

```bash
ros2 launch my_robot_bringup luckrobot_system.launch.py \
  mode:=mapping navigation_profile:=luck_full \
  depth_obstacle_mode:=height
```

先手持平板从 0.6 m 缓慢移近，确认 RViz 局部代价地图出现障碍且
Collision Monitor 能制动；再做不超过 0.8 m 的 0.05 m/s 低速直线测试。
验证通过前不要运行自动探索，也不要让机器人驶入桌下。

## 安全边界

深度相机约 0.15 m 内存在物理盲区，透明、镜面、纯黑和细线状物体也可能没有
可靠深度。软件扫描不是安全认证传感器。最终样机仍建议在最高结构前缘增加实体
防撞条/触边开关，或让刚性保护框成为全机最高点。

## V12.10.3 动态改路验收

使用 `depth_obstacle_mode:=height` 启动后，让机器人背对一个只会撞到上部结构、
不会被 2D 雷达击中的平板，然后在 RViz 发布平板后方目标。初始路径可能穿过平板；
相机转向后应先在局部代价地图出现障碍，并在约 2～3 秒内看到全局路径绕开或导航
安全停止。若周围空间不足以绕行，停止而不是强行保持原路线同样属于正确结果。

诊断包可检查近距回波是否只是短时噪声：

```bash
python3 ~/ros2_ws/tools/analyze_depth_scan_noise.py \
  ~/custom_nav_YYYYMMDD_HHMMSS_bag /scan_camera 0.45
```

V12.10.4 验收时重点观察：第一次看到高位障碍后，即使转向导致障碍离开相机视场，
全局代价地图中的障碍及绕行路径仍应稳定保持；不得在 16 秒内重新切回穿越障碍的
直线。若障碍被人工移走，约 16 秒后恢复最短路线属于预期行为。

## V12.10.5 噪点与双通道验收

正式启动后应同时看到两个约 15 Hz 的话题：

```bash
timeout -s INT 8s ros2 topic hz /scan_camera_safety
timeout -s INT 8s ros2 topic hz /scan_camera
ros2 topic info /scan_camera_safety -v
ros2 topic info /scan_camera -v
```

预期连接关系：Collision Monitor 订阅 `/scan_camera_safety`；局部和全局代价地图
订阅 `/scan_camera`。RViz 中显示的规划扫描仍为 `/scan_camera`。空旷直行时，
偶发的单帧前方点允许出现在安全流，但不应进入规划扫描或形成持续膨胀块。真实平板
放在 0.25～0.60 m 处后，规划扫描应在约 0.20～0.50 秒内稳定出现，机器人应绕行
或安全停车。不要通过缩短 6/16 秒记忆来掩盖噪声，否则转弯后忘记高位障碍的问题会
重新出现。
