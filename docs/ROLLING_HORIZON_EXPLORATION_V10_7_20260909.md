# 连续滚动目标与执行反馈看门狗（V10.7 / V11.9，2026-09-09）

## 1. 本轮结论

`auto_diag_20260909_123011` 证明当前自定义 Nav2 已能承担自动探索：122.3 秒内发送
4 个目标，轮式里程累计约 4.60 m，新确认地图面积约 6.68 m²，未被 Collision
Monitor 篡改运动指令。该包中的主要问题不是全局规划失败，而是两个相互独立的时序
问题：

1. V10.6 必须等当前 0.6～1.2 m 落脚点返回成功，才计算下一个目标，形成明显的
   “减速—停住—再启动”。
2. LuckController 的执行看门狗只观察 `/odometry/filtered`。约第 64.1 秒时，
   `/cmd_vel_safe` 正在要求原地转动且两轮反馈为相反方向约 6 RPM，
   `/wheel/odom` 也报告约 `-0.215 rad/s`，但当时 IMU 为零并把融合角速度压到约
   `-0.007 rad/s`，看门狗因而把真实运动误判成底盘未执行。

所以本轮不再修改已经通过大量单点测试的速度、曲率、膨胀半径、footprint 或
Collision Monitor。

## 2. V10.7 滚动视野接力

探索器仍以已知白色区域作为 Nav2 目标，以可观测 UNKNOWN 连通区域作为信息收益，
并保留宏观分叉记忆、LIFO/DFS 回退和完成判定。新增的接力只在以下条件全部满足时
发生：

- 当前目标已经执行至少 2.0 秒；
- 机器人距当前安全落脚点不超过 0.45 m；
- 当前分支仍存在，并且新候选属于同一个 UNKNOWN basin；
- 新方向相对当前分支不超过 0.52 rad（约 30°）；
- 新目标至少把路线向前延伸 0.20 m；
- `LuckGrid` 对新白色目标的路径预检成功。

满足时，新的 `NavigateToPose` 会作为同一 action 的目标更新发出，使控制器沿原分支
继续行驶，而不用先停在人工分段点。若候选或规划预检失败，探索器保留当前目标，不会
为了追求连续性取消一条仍然安全的路线。跨分支、DFS 回退、硬代价等待和最终收敛仍走
原有的保守状态机，避免在岔路口提前乱跳。

这是一种受约束的 receding-horizon（滚动时域）方法，不是简单地每隔固定时间发布
目标。它能减少正常前进段的停走，同时不牺牲可达性检查和分支覆盖。

## 3. 自动结束

以下逻辑保持有效：

- 已观测或收益不足的灰区不会重复产生目标；
- 完成分支只有新增足够 UNKNOWN 面积时才重新打开；
- 当前分支末端经等待确认后回退到最近的有效兄弟分支；
- DFS 栈清空且连续 15 秒没有安全候选时，发布探索完成并停止。

因此“持续探索全屋”和“没有可探索区域后自动结束”由同一状态机实现，不采用固定
运行时长作为完成条件。

## 4. V11.9 执行看门狗修正

导航与控制继续只使用 `/odometry/filtered`，不会绕过 EKF。新增的
`/wheel/odom` 订阅只用于回答“底盘有没有实际执行非零指令”：任一新鲜里程计确认
线速度或角速度超过阈值，都视为存在运动。这样保留融合里程计作为控制基准，同时避免
IMU 短时停报或融合延迟导致错误重规划。

该修正不会掩盖真实卡死：如果融合里程计和轮式里程都没有运动，原来的有界失败、
行为树清图/等待/重规划仍会触发。

## 5. 实车验收

部署后必须关闭旧探索进程并重新启动终端 1，使新的控制器动态库和参数进入运行进程。
一次从房间中部启动，一次从边角启动，各记录至少 5 分钟：

```bash
cd ~/ros2_ws
source /opt/ros/humble/setup.bash
source ~/ros2_ws/install/setup.bash
bash ~/ros2_ws/tools/run_auto_diag.sh 300
```

重点查看：

- 启动日志出现 `Rolling-horizon UNKNOWN-branch exploration V10.7`；
- 同一分支接近落脚点时出现 `rolling-handoff`；
- 接力期间底盘没有完整停稳再起步；
- 中部起步能依次进入宏观分支，不在小碎角间往复；
- 所有有效 UNKNOWN 分支结束后能够自行报告完成；
- 若出现失败，诊断包同时包含 `/odometry/filtered`、`/wheel/odom` 和三级
  `cmd_vel`，可区分规划、控制、安全层和执行反馈。
